## Intent

**Problem:** Epic 5 ends at the numbers. Ten KPI cards, seven charts, a handler table and a top-30 worklist all render figures no one can open — `renderSV` in the prototype is inert markup with not one `onclick` on a dashboard surface, and the console inherits that: `KpiCard` renders a `<section>`, chart legend rows are `<li>`, and Story 5.4 deliberately shipped its table **without** an `onRowClick` rather than declare a prop that type-checks and does nothing. There is no endpoint that answers "which claims are behind this number" — `GET /claims/queue` takes one of eight operational filters, is caller-scoped, and covers four of the ten cards and none of the chart facets.

**Approach:** One new scoped aggregate, `services/worklist/drill_through.py`, behind `GET /dashboard/claims` — a cursor-paginated, priority-ordered claim list narrowed by a whitelist of twelve `filter[…]` facets, each of which resolves through the **same registered derivation and JDM threshold as the surface that was clicked**. Two new routed views under the dashboard: a filtered list that reuses Epic 2's queue card, and a read-only claim view composed from the pure presentational pieces of Epic 2/3's case file. Then click-wiring across every 5.1–5.4 surface. The read-only view needs **no server change at all**: `GET /claims/{id}` is already scope-only, already 404s out of scope, and already carries the header, stage overview, reserve verdict and documents; the money figures are on the stage variant the payload already sends.

## Boundaries & Constraints

**Always:**

- **Scope is never a filter.** `employer_scope(ctx)` is the only scope predicate and it stays on the WHERE clause; `filter[employerId]` and `filter[handlerId]` **intersect** the caller's book and can never widen it. There is nowhere in any signature to put a scope, and it stays that way — a smuggled `employerId` outside the book yields an empty page, never a 403 and never a row (AD-7).
- **Every filter reconciles with the surface that opened it, and a test proves the number.** `stage`/`severityBand`/`fraudFlagged`/`litigation`/`surgery`/`oshaRecordable` are the *exact* predicates `summary.py` counts with — `severityBand` through `risk.of(severity_score)`, `fraudFlagged` through the `fraud_flagged` derivation (`fraud_flag and fraud_score >= fraud_flag_score_min`, **not** `siu_review`'s higher cut), `stage == settled` and **not** `status == settled_closed`. `recoveryStatus`/`injuryType`/`state`/`employerId` are `charts.py`'s exact fold keys, injury type and state matched as the **exact stored string** with no trim, case-fold or merge. `priority` is `priority_claims`' own population predicate, **imported as one symbol**, not restated (AD-10).
- **Ordering is `priority.order_key` over `priority.priority_score`** — the symbol Story 5.4 extracted, with no second sort anywhere and no `sort` query parameter.
- Page size is `priority_weights.page_limit`, read from the rule document, never a caller's choice. The cursor carries the filter set, `offset`, `as_of`, `limit`, and the `priority_weights` + `derivation_thresholds` versions; every one is re-validated on decode against what is effective **today**, alongside offset bounds, page-size bounds and `MAX_CURSOR_AGE`.
- One scoped read for the list (`select_drill_rows`); filtering, ranking, counting and paging are Python over derived rows, because `select_queue_rows`' docstring already ruled that this module decides *which rows* — scope, and nothing else.
- `Cache-Control: no-store` as the first statement of the route body and restated inside every `ProblemException`; no audit event; camelCase over `ApiModel` built field by field; `{items, nextCursor, total}`; business ids `WC-nnnn`; problem+json on refusal.
- **Read-only means absent, not disabled.** The read-only claim view is *composed from* pure presentational components; it does not render an edit control behind a flag, and it calls no endpoint that writes.
- The SPA renders what arrived. No client sort, filter, count, slice, accumulation or threshold comparison — `noDerivation.test.ts` scans every new file under `features/dashboard/` and must be extended to name each one.
- Filter state lives in the URL query string using the **same** `filter[…]` names the API takes, so the URL and the request agree; TanStack Query keys include the filter set.
- Every click target is a real `<button>` or `<Link>` with a visible focus ring, never a `div onClick`.

**Block If:**

- `GET /claims/{claim_business_id}` turns out to write, or to be role-gated against supervisor/analyst. The read-only view rests entirely on it being a pure scoped read; **`GET /claims/{id}/financials` is explicitly not usable** — its own docstring says "This GET can write", refreshing `payment_schedule_week` before reading it, and a read-only surface triggering a write is not a call to make unattended.
- Publishing `handlerId` on `HandlerBenchmarkResponse` cannot be done additively — i.e. some consumer or test asserts that response's field set is closed. Rank-by-name would be the alternative and it is not one: two handlers may share a display name, and `benchmarks.py` already groups on `handler_id`.
- The seeded book turns out to hold fewer claims than one page (`priority_weights.page_limit`, 50) for the **full-portfolio** persona, so the cursor is never exercised end to end. Do not lower the page limit to manufacture a walk.

**Never:**

- No new rule document and no migration. The page size is `priority_weights.page_limit`, which already means "page size of a priority-ordered claim list" and whose version the cursor must record anyway for the ordering; 5.4's argument was against *superseding* that document, not against reading it.
- No `sort` parameter, no client-selectable page size, no `scope` parameter of any spelling.
- No aggregate or dashboard-scope copilot, no copilot pane on the read-only view (architecture-deferred).
- No export, no cohorts, no deep segmentation — Epic 7 builds on this endpoint; do not build its features.
- No edit affordance on the read-only view, including a disabled one; and no `readOnly` prop threaded through `features/claim-detail/` — the handler workspace's four mutation leaves are not touched by this story.
- No second refusal shape: `400` stays reserved for `/problems/invalid-cursor`; an invalid enum filter value is the global handler's **422 `/problems/validation-error`**, and an unknown *parameter name* is ignored, as it is everywhere else.

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|

| Defined empty | `filter[litigation]=true` as Park | `items: []`, `total: 0`; view renders an empty state **naming the active filter** | No error expected |

| No session | no cookie | 401 problem+json | — |
| Second page fails in the SPA | `nextCursor` request rejects | Loaded rows stay, inline `role="alert"`, a "Reload this list" escape hatch that does not replay the rejected cursor | Retrying the cursor is not offered |

## Design Notes

**1. The filter table is the story's real architectural move, and reconciliation is what makes it one.** Ten cards, six chart families, a handler table and a worklist are four different ways of counting the same book, and the failure mode this story is most exposed to is a drill-through that opens a *plausible* list — the 9 SIU claims behind a card that counted 13 fraud-flagged ones, the 54 `settled_closed` claims behind a donut slice that folded 62 by stage. Every one of those pairs already exists in this codebase as a recorded near-miss. So the twelve predicates are one table in one module, each entry calling the clicked surface's own derivation, and the tests do not compare against constants: they read the KPI endpoint and the drill endpoint on the same scope in the same test and assert the two numbers are equal. A constant would pass while both surfaces were wrong together.

**2. No new rule document, and the page size is already written down.** `priority_weights.page_limit` means "page size of a priority-ordered claim list"; the queue is such a list and so is this one. The cursor has to record that document's version anyway, because the *ordering* reads it — so reusing the field costs nothing and inventing a `drill_through` document would cost a migration to publish a number the project already publishes. 5.4's argument was against **superseding** `priority_weights` to add a field the queue does not read; reading a field it already has is the opposite operation.

**3. The two money cards, and what a drill-through owes its number.** Total Paid and Total Reserve are sums of cents, not counts of claims; the set they summed over is the whole scoped book, which is exactly what Total Claims opens. So all three land on the unfiltered list, and that is honest rather than lazy: the alternative — ruling them non-navigable — would make two of ten cards dead ends for no gain, and the alternative to *that*, a "filter" naming the card, would invent a URL concept that is not a filter and cannot be cleared. One caveat is recorded rather than fixed: `total_paid` excludes bills in `status=paid` (a known product gap, ~$335,985 over 38 claims), so if a future column on this list shows per-claim paid, it will not sum to the card. That decision has an owner and it is not this story.

**4. Four SLA tiles ruled non-navigable, and the reason is a guard, not laziness.** `test_nothing_outside_the_worklist_aggregation_reads_the_sla_source_columns` confines the three duration columns to `sla.py`, so a `filter[slaBreach]` would have to be evaluated inside that module over rows this aggregate does not read — a second scoped read on a route whose whole discipline is one. And the tile UI does not distinguish *which* clock a cohort belongs to, so the filter would need a vocabulary the surface cannot express. The honest fix is a cohort predicate exported from `sla.py` and a thirteenth facet, made once; it is recorded in `deferred-work.md` with that recommendation rather than half-built here. The story text explicitly sanctions ruling a tile non-navigable with a reason, and this is the reason.

**5. Read-only is composed, not flagged.** The tempting shape is a `ClaimViewMode` context read by `InlineEditField`, `ActionsCard`, `AddInjuryPopover` and `LineItemDialog` — four leaves, one edit, done. It is the wrong shape twice over. It puts a mode flag on the handler workspace's hottest components, so every future edit affordance is correct only if its author remembers the flag; and it makes "no edit controls" a property of a boolean rather than of the tree, which means the test that proves AC 2 is really testing a prop. Composing the read-only view from the pure pieces — `CaseHeader`, `RiskGauge`, `StageStepper`, `Cards.tsx`, `DocumentList` — costs one new file, touches nothing in `features/claim-detail/`, and makes the affordances structurally impossible. The epic context already ruled the words: read-only means **absent**, not disabled.

**6. `filter[…]` brackets here, a scalar `filter` there, and both are right.** `/claims/queue` selects one of eight operational *modes* — `high_risk` and `payment_due` are not independent dimensions a handler intersects, they are alternative ways to look at one queue. This route intersects independent facets, which is what the architecture's list convention spells with brackets. The two spellings mean different things and the router docstring says so, because the next reader's first question will be why they differ.

**7. The cursor refuses a changed filter set, and that is the queue's ruling, not a new one.** An offset cursor into a filtered ranking is only meaningful against the ranking that produced it; replaying it under different filters would page into a different list at the same offset and silently skip or repeat. `test_claims_queue.py` already refuses this with a 400, and this story copies the refusal rather than inventing a merge.

**8. `handlerId` on the wire is an additive publish, not a new fact.** `benchmarks.py` has grouped on `handler_id` since 5.2 (L222-228) and publishes only the name, which is exactly the shape `EmployerPaidResponse` deliberately avoided by shipping `employer_id` — the field comment there says it is for this story. Two handlers sharing a display name is not hypothetical enough to bet a scope-sensitive filter on.

**Review:** one pass, two adversarial reviewers, no intent gap and no bad spec. 9 patches, 2 deferred with evidence, 3 rejected. Four mattered. The route was **ungated on a wrong argument about its own payload**: `filter[handlerId]` was justified as attributing no metric to the handler, but `total` under that facet alone is precisely the `caseCount` figure the benchmarks route 403s a handler for reading — reproduced live, a handler getting 403 from one route and 200 from the other for the same number, with ids small enough to enumerate. The story's own test asserted the equality that made it leaky. An invalid filter value produced a **permanent error with no chip to clear it** and copy promising a retry the client refuses to perform. The read-only view's Back control **discarded the filter set**, contradicting the page's own premise, with a test pinning the defect. And `toQueryParams` **documented a compile-time guarantee its return type erased** — a facet renamed on the server would have typechecked green and silently opened the unfiltered book; typing it against the generated document immediately exposed four value conversions the loose annotation had been hiding.

**Residual risks.** The endpoint ranks the caller's whole scoped book per page request — free at 100 claims, and the third list with that shape; its cursor is an offset, so a claim leaving the filtered population mid-walk slides the window. Both are recorded, and both now have three call sites, which is the argument for fixing the idiom once rather than here. The drill list's rows are buttons rather than links, so the story's own read-only route cannot be opened in a new tab from the list built to reach it — deferred because `ClaimCard` is shared with the handler queue, where `onSelect` sets a query parameter rather than navigating.
