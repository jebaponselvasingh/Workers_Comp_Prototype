## Intent

**Problem:** The `bak` container has been in the deployment view since the architecture was written and has never been built. There is no `pg_dump`, no WAL archive, no off-host copy, no encryption of anything that leaves the host, and no restore procedure — so a host loss is total claim-data loss, and nobody can say otherwise because nothing has ever been restored. Epic 8 hardened the stores (8.1 purge, 8.2 pgaudit/TLS) on top of a system with no disaster recovery at all.

**Approach:** One `backup` container that owns the whole pipeline: nightly `pg_basebackup` + `pg_dump` + a tar of the blob volume, each encrypted with `age` to a recipient public key **before** anything is copied off-host, plus a continuously-streaming `pg_receivewal` so the archive is replayable rather than decorative. Every run writes a machine-readable status file that the container's own healthcheck reads, so a failed run — or a scheduler that silently stopped — shows as `unhealthy` in `docker compose ps` beside every other service. And a runbook in `deploy/RESTORE-DRILL.md` that is **executed** against a clean stack as part of this story, with the real steps, wall-clock duration, deviations and completed checklist recorded in it.

## Boundaries & Constraints

**Always:**
- **Encrypted before it leaves the host, with no key that can decrypt it on the host.** `age` public-key encryption to `BACKUP_AGE_RECIPIENT`. The identity (private key) lives only in the operator's secret store, never in the backup volume, never in the image, never in VCS, never in the artifact set. A plaintext artifact never reaches the off-host destination — encryption happens first, the copy second, and a failure of the first means there is nothing to copy.
- **One stream covers the whole instance (AD-3).** `pg_dump -Fc` of database `lineworker` carries every PHI-class store — relational entities, `claim_embedding`/`knowledge_*` vectors, the vendored LangGraph checkpoint tables, `ai_insight`, `audit_event` — in one artifact, plus one tar of the blob volume. No per-store backup path, ever; that single stream is the load-bearing rationale of AD-3.
- **Backup output is names, sizes, counts, timestamps and exit codes — never data content (AD-11).** That binds the status file, the manifest and every log line the container emits.
- **The backup container's health is derived from its own last run.** Unhealthy when the last run failed, or when no successful run exists within `BACKUP_MAX_AGE_HOURS` of the later of (last success, container start) — so a scheduler that quietly stopped surfaces the same way a failed `rsync` does.
- **No schema change, no new table, no new DB role, no widened grant.** The job connects with the existing owner role (which already holds `REPLICATION` in this deployment) and reads. AD-4's posture is untouched.
- **Same service, same mechanism, in dev, e2e and prod** — 8.2's anti-drift rule — with the differences confined to what must differ (scheduling on/off, WAL on/off, destination), and a posture test that fails when the three disagree.
- **Every knob is 12-factor env config**; the two with no safe default (`BACKUP_AGE_RECIPIENT`, `BACKUP_REMOTE`) carry `${…:?}` guards in the prod overlay, matching `TLS_CERT_DIR`/`PG_TLS_DIR` from 8.2.
- **`docker compose -f deploy/compose.yaml up` on a clean checkout keeps working** — Story 1.1's promise. The backup service is therefore profile-gated in the dev and e2e profiles and always-on in prod.

**Block If:**
- The drill cannot be executed at all (container runtime unavailable, images unbuildable) — an unexecuted runbook does not satisfy AC 2, and recording one as executed would be a lie in a compliance document. HALT with the evidence rather than shipping it.
- Making the backup work appears to require a new DB role, a widened grant, a schema change, or `ENV: prod` — all of which contradict AD-4, this story's data note, or the standing 8.2 finding. HALT rather than deciding it unattended.

**Never:**
- Never purge-aware backup filtering. A restored backup can resurrect purged PHI; the mitigation is bounded backup retention plus a stated operational caveat in the runbook, per the story's explicit instruction.
- Never an `age` identity, an SSH private key, a certificate or an off-host credential committed to VCS or written into the backup volume.
- Never a second backup path per store, and never a MinIO/S3 blob backend (deferred decision) — this story creates the blob *volume* the backup covers, nothing more.
- Never monitoring/alerting integration (deferred observability decision): the status file plus the healthcheck are the whole binding surface.
- Never health endpoints on other containers, prod-profile completion, or the deferred-decision registry — those are 8.4.
- Never `archive_command` on the shared postgres service (see Design Note 1), and never `ENV: prod` reintroduced anywhere.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|---|---|---|---|
| Nightly run, all reachable | DB up, recipient set, destination writable | `artifacts/<runId>/` holds `base.tar.gz.age`, `dump.age`, `blobs.tar.age`, `wal/*.age`, `manifest.json`; copied to `$BACKUP_REMOTE/<runId>/`; shipped WAL removed locally; runs beyond `BACKUP_KEEP_RUNS` pruned both sides; `status.json` `result: success`; healthcheck exits 0 | No error expected |
| One-shot invocation | `docker compose run --rm backup once` | Exactly one run, no scheduler loop, no WAL receiver; process exit code is the run's | Non-zero exit on any failed stage |
| Off-host destination unreachable | `BACKUP_REMOTE` points nowhere | Encrypted artifacts stay local; `status.json` `result: failure`, `stage: copy`; nothing pruned | Exit non-zero; healthcheck exits 1; `error` field carries the command's exit code and stderr's **first line**, never file content |
| No recipient configured | `BACKUP_AGE_RECIPIENT` empty | Refusal **before** `pg_dump` runs — no plaintext artifact is ever created; `status.json` `result: failure`, `stage: config` | Exit non-zero; healthcheck exits 1 |
| Database unreachable | postgres down mid-run | `status.json` `result: failure`, `stage: base` or `dump`; the partial run directory is removed | Exit non-zero; healthcheck exits 1 |
| Fresh container, no run yet | Container started 5 min ago | Healthy — nothing has been missed yet; the window is measured from container start | No error expected |
| Scheduler stopped silently | Last success 30 h ago, `BACKUP_MAX_AGE_HOURS=26` | Healthcheck exits 1; `docker compose ps` shows `unhealthy` | This is AC 3's surfacing |
| WAL receiver dies | `pg_receivewal` exits while the loop runs | Restarted with bounded backoff; `status.json` carries `wal_streaming: false` until it recovers; a run that finds it down still dumps | Recorded, not fatal to the dump |
| Replication slot outlives the receiver | Backup container down for days | Postgres invalidates the slot at `max_slot_wal_keep_size`, so the data volume cannot fill; next receiver start recreates it and the WAL gap is recorded | Gap is visible in `status.json`, never silent |

## Design Notes

**1. `pg_receivewal` from the backup container, not `archive_command` on postgres.** The story offers both. `archive_command` puts backup concerns inside the database service: either `age` and the recipient key go into `deploy/postgres/Dockerfile` — a file whose 8.2 comment says it holds pgaudit and nothing else — or WAL lands in a shared volume in plaintext and is encrypted later anyway. Worse, an `archive_command` that fails does not skip: Postgres retains WAL indefinitely and eventually stops accepting writes, so a broken backup becomes a database outage. `pg_receivewal` keeps every backup concern in the backup container and needs no new role — the owner role already carries `REPLICATION` in this deployment. **It needs two changes to the postgres service, not one**, and the second was found by running it rather than by reasoning about it: the official image appends only `host all all all scram-sha-256`, and `all` in the database column does not match a *physical replication* connection, so both `pg_basebackup` and `pg_receivewal` fail with `no pg_hba.conf entry for replication connection`. Hence `deploy/postgres/pg_hba.conf`, mounted read-only and named by `-c hba_file=` in all three profiles — the same mechanism, and the same argument, as Story 8.2's `command:` list. It adds no role, no grant and no privilege; it makes an attribute the owner role already has reachable over the internal network. Its own failure mode (an abandoned slot pinning WAL) is exactly what `max_slot_wal_keep_size=2GB` bounds: the slot is invalidated, the receiver fails loudly, the status file records the gap, and the database keeps serving.

**2a. `-X stream`, not `-X fetch`, and a bounded spool.** Review corrected two things about the WAL half. `pg_basebackup -X fetch` collects the required WAL at the end of the backup and is the one mode documented to fail with "requested WAL segment has already been removed" — on a busy database, or a slow base backup, or exactly the profiles that turn the persistent slot off. `-X stream` is equally self-contained (it writes `pg_wal.tar.gz`, now part of the artifact set) and takes a temporary slot for the duration, which is what makes the guarantee hold. Separately, segments leave the local spool only after a successful off-host copy — so a destination that is unreachable for a week would have grown it without bound on a volume that by default shares a filesystem with `pgdata`, and the database would have stopped accepting writes. That is the outage `max_slot_wal_keep_size` was added to prevent, moved one directory to the left. `BACKUP_MAX_SPOOL_SEGMENTS` bounds it, drops the oldest, and records `wal_dropped` — a **recorded** gap in the point-in-time archive rather than an unrecoverable host, which is the same trade the server-side bound makes.

**2. Why there is a base backup as well as a dump.** The story's Task 4 says "`pg_restore` + WAL replay to target time" — those two do not compose. WAL is the physical write-ahead log of a specific data directory; it replays onto a physical base backup, never onto the logical objects `pg_restore` recreates. Shipping a WAL stream with only a `pg_dump` to pair it with would be shipping an archive that cannot be used, which is precisely the "aspirational, not provable" failure Epic 8 exists to close. So each run takes both: `pg_dump -Fc` is the portable artifact the drill restores and the one that survives a major-version change, and `pg_basebackup -Ft -z` is what makes the WAL stream mean something. RPO: 24 hours from the dump alone; approximately the unflushed tail of the current WAL segment when recovering base + WAL. Both numbers go in the runbook, because "we have backups" without a recovery-point number is the thing this story is replacing.

**3. A 60-second poll loop rather than cron or supercronic.** Debian's `cron` in a container does not see the container's environment — the classic fix is dumping `env` to a file at start, which is a second copy of the configuration and a silent-failure surface in a story about eliminating silent failures. `supercronic` solves that properly but arrives as a pinned binary downloaded from GitHub at image build, which this project has no precedent for and which the standing "locally built image breaks pull-only deployments" deferral already argues against widening. A loop that wakes each minute, compares `%H:%M` to `BACKUP_AT` and checks whether today already ran needs no package, no env plumbing and no cron syntax, and it is stop-friendly — a `sleep` spanning a night would ignore SIGTERM until morning. The failure mode the story actually cares about, a scheduler that stopped, is caught by the healthcheck's staleness window rather than by trusting any scheduler.

**4. `age`, and the identity is not on the host.** `age -r <recipient>` is public-key encryption with no keyring, no agent, no interactive prompt and one small dependency — which is what a non-interactive nightly job needs. GPG would work and brings a keyring, a trust model and a home directory to manage inside a container. The load-bearing property is not the algorithm: it is that the backup host holds only the **recipient**, so compromising the host — the exact scenario off-host backups exist for — yields no ability to read any backup, past or future. That is why the runbook's first prerequisite is fetching the identity from the operator's secret store, and why the e2e profile can commit a recipient with no identity anywhere.

**5. The blob volume is created here because the backup must cover it.** `VolumeBlobStore` exists, is not wired into the app, has no setting and no compose volume, and every seeded `blob_key` is null — so there are no bytes to lose today. A backup that covers only what exists today would be a backup that silently stops being complete the moment binaries land. The volume is declared, mounted read-write into `api` at the path `scripts/purge_claim.py --blob-root` wants and read-only into `backup`, and tarred into the artifact set from birth. Choosing the storage backend stays deferred; giving the current one a location does not decide it.

**6. Health measured from container start, not from epoch.** "Unhealthy when no successful run within 26 hours" is right for a container that has been up for days and wrong for one that started a minute ago — the literal reading makes every fresh stack unhealthy and `docker compose up --wait` fail. Measuring the window from `max(last_success, container_start)` says what is actually meant: this container has not missed a backup it was responsible for. The e2e profile never exercises it via `up` anyway, because the service is profile-gated and the spec drives `run --rm`.

**6a. Plaintext is swept, not merely trapped.** The staging directory holds an unencrypted `pg_dump` of the entire claim book for the seconds between the dump and the encrypt stage, and it was removed only by the EXIT trap — which is precisely what does not run on a SIGKILL, an OOM, or a `docker compose down` that outlasts its ten-second grace period during a base backup that takes minutes. A trap is a promise about orderly exits; AD-11 needs a property that survives disorderly ones. So there are three mechanisms rather than one: `stop_grace_period: 300s` gives an orderly exit time to happen, signal traps make a signalled run exit through the same path a failed stage does, and both `entrypoint.sh` (at container start) and `backup.sh` (at run start) sweep any staging directory a previous life left behind. The same sweep removes manifest-less run directories, which the retention count would otherwise treat as backups and retire a real one to make room for.

**7. The drill runs against the e2e profile, and that is recorded as a deviation.** A drill against the dev profile pulls several gigabytes of Ollama models before anything is healthy, and the prod profile is not bootable at all — no certificates in VCS, and `ENV: prod` still refused by `create_app` (the standing 8.2 finding that 8.4 owns). The e2e profile runs the same api, web and postgres images with a deterministic model stub, which is also the stack the `@smoke` set is written against. The drill is therefore real — a destructive `down -v` and a restore from the encrypted artifact alone — on the profile this repository can actually boot, and the runbook says so rather than implying a prod rehearsal that did not happen.

**8. The drill's own finding: a backup that restores into an unusable database.** The first execution of Procedure A restored `dump.age` on its own into a fresh cluster. `pg_restore` printed `errors ignored on restore: 69` and **exited 0**; every row of data was present and correct; and the result was a database the application could not open, because `lineworker_app` did not exist — nor did `audit_redactor`, nor its two grants, nor the five row-level-security policies that are the AD-4 audit invariant. `pg_dump` dumps a *database*; roles are cluster-level and are not in it. This is the exact failure mode Epic 8 exists to close — a backup that looks fine until the day it matters — and it was invisible to every other check in this story, because the round-trip test restores into a scratch database *in the same cluster*, where the roles already exist. The fix is a `pg_dumpall --globals-only` artifact, a restore-globals step in Procedure A with a grant-count check that catches its omission, and a test that decrypts the artifact and asserts both roles are in it. Recorded here rather than only in the runbook, because the lesson is about what a restore test in the same cluster cannot see.
