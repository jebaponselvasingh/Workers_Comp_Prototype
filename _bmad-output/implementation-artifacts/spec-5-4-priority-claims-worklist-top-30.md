## Intent

**Problem:** The supervisor dashboard ends at the charts. The one surface that turns portfolio numbers into tasking — the table of claims that actually need a handler's attention — does not exist, and the prototype's version is wrong twice over: it takes the first 30 claims in dataset order rather than the 30 highest-priority ones (`claims.filter(…).slice(0, 30)`, L1056), and it fills its "Priority Next Best Action" column from `cpNextActions[0]`, a pre-authored copilot string.

**Approach:** One scoped aggregate, `services/worklist/priority_claims.py`, that reads the caller's book once, scores every claim with **Story 2.1's** scorer, cuts the active-treatment ∪ fraud-flagged ∪ litigation population to a JDM-owned cap, and fills the action column with the top row **Story 3.5's** deterministic generator returns. A cursor-paginated `GET /dashboard/priority-claims` serves it, and a hand-written table renders exactly what arrived.

## Boundaries & Constraints

**Always:**
- Ordering is `priority.priority_score` and nothing else. The `(-score, claim_id)` sort key currently lives inline in `queue._ranked_group`; extract it into `priority.py` and have both callers use it, so "the same scorer" is a fact about the code rather than a claim in a docstring (AD-2, AD-10).
- Every derived cell resolves through a registered computer: `risk` (severity band), `days_open`, `fraud_flagged` (the population arm and the score's tone — 5.1's card threshold, **not** `siu_review`'s), `siu_review`/`rtw_blocked`/`payment_due` (the scorer's flags). `litigation_flag` is a stored column and stays one.
- The population arm "active treatment" is `stage == treatment`, Story 5.1's stage-over-status ruling.
- The cap and the page size are JDM parameters — no literal bounds a list in Python. The one exception is the cursor's own validation range (`MIN_PAGE_LIMIT` / `MAX_PAGE_LIMIT` / `MAX_CURSOR_AGE`), which `queue.py` and `notes.py` already spell as module constants because they guard a decoded string rather than tune the business.
- The scoped read happens once, behind `employer_scope(ctx)`; the four per-claim action sources are read in bulk over the page's ids. No role branch anywhere in the path.
- `Cache-Control: no-store`, no audit event, camelCase over `ApiModel`, `{items, nextCursor, total}`, business ids `WC-nnnn`, problem+json on refusal.
- The SPA renders what arrived. No client sort, filter, accumulation, truncation-by-count or threshold comparison.

**Block If:**
- Superseding `worklist_actions` to v2 with two required keys would break any caller that resolves the document at an `as_of` before the new version's `effective_from` — making the new parameters optional is a rules-tier precedent this project does not have, and inventing one unattended is not this story's call.
- The seeded full-portfolio population turns out to be at or below the cap, so the cap is not exercised end to end. Do not lower the cap to manufacture a test.
- `generate_actions` cannot be driven from bulk-read inputs without changing its signature.

**Never:**
- A second priority scorer, a second action generator, a second definition of the cap, or any re-weighting for this surface.
- Any LLM path near the action column. The `ai_insight` cache is not a source here; Epic 6's narrative "next best actions" card is a different, later thing.
- Row click, drill-through, `onRowClick` wiring, or any mutation — 5.5 makes rows clickable; this table is read-only by construction, so no command, no audit event, no toast.
- A `limit` query parameter. Page size is a published rule, not a caller's choice, and `test_query_parameters_cannot_widen_or_change_the_scope` keeps `?limit=20` inert.
- `getSortedRowModel` / `getFilteredRowModel` / `.sort(` / `.reduce(` anywhere under `features/`.
- Truncating the injury-type or action text in JavaScript. The prototype's 22- and 48-character cuts become CSS truncation with the full string in `title`.

## Design Notes

**1. The extraction is the story's real architectural move.** AD-2 says the scorer exists once, and it does — but its *ordering* does not: `(-score, claim_id)` is a lambda inside `queue._ranked_group`, and a second surface that "sorts by the same scorer" would be one `reverse=True` away from a table that agrees with the queue on every score and disagrees on every tie. Ties are not hypothetical here; the seeded book has many, and the cursor's stability depends on the tie-break being total. Extracting `order_key` costs one function and converts "the same ordering" from a claim in a docstring into a shared symbol, which is what makes the equality test meaningful rather than circular.

**2. Five reads, not forty.** `actions.claim_actions` is the natural-looking entry point and the wrong one: it performs six scoped reads and two document loads *per claim*, so a ten-row page would cost forty round trips and a full walk a hundred and twenty, on a route with no cache, beside three other aggregates that each take one. The pure `generate_actions` is the seam the module already built for this — its docstring says the flags and parameters arrive resolved — so the four child sources become bulk reads over the page's ids and the parameter blocks load once. Cost: four new repository functions. Benefit: this aggregate looks like the other three — parameters injected by the route, reads counted by a test — and `test_the_aggregate_takes_exactly_five_scoped_reads` keeps it that way.

**3. Two numbers, one document, and the cursor is the reason.** The cap could live in `priority_weights` beside `pageLimit`, and superficially belongs there. It must not: the queue's cursor records the `priority_weights` version, so publishing a v2 of that document to add a number the queue never reads would invalidate every outstanding queue cursor — exactly the cost `deferred-work.md` recorded when `pageLimit` was placed there, paid again for nothing. `worklist_actions` is already loaded by this path for the action column, is owned by the same service, and already holds the family's other list-length knobs (`cap`, `paddingFloor`). The names carry a `supervisorWorklist` prefix because that block's existing `cap` means something else entirely.

**4. Page size is a rule, not a parameter.** Every dashboard route today declares zero parameters, and `test_query_parameters_cannot_widen_or_change_the_scope` asserts that `?limit=20` cannot move the answer. Honouring the story's cursor requirement means adding exactly one parameter — `cursor` — and leaving the page size in JDM, where a caller cannot reach it. The contract test becomes an allowlist of one rather than an assertion of emptiness, and the smuggling test survives verbatim, `limit` included. The page size (10) is deliberately below the cap (30) so the cursor is exercised by the seeded book rather than by a hypothetical one, and it bounds the action generation to ten claims per request.

**5. The diary check-in makes this column reader-relative, and that is the existing ruling rather than a new bug.** `select_latest_note_at` is scoped to the caller's *own* diary, with an argued docstring: counting anybody's note would publish a handler's private working record to whoever else read the claim. A supervisor has no notes on these claims, so `latest_note_at` is `None` for every row and the diary rule fires — meaning one claim's "next best action" can differ between the supervisor's table and the handler's checklist. The blast radius is small and bounded by construction: `urgencyDiaryCheckIn` is `low`, and `_rank` sorts on urgency first, so the row only reaches position zero when nothing medium or high fires — which, on a population defined as treatment ∪ fraud ∪ litigation, is rare. Passing the *handler's* note time instead would be the leak the existing docstring refuses. Recorded rather than corrected, with a test that pins the behaviour to `latest_note_at=None` so it cannot change silently.

**6. Ungated, and the discriminator is unchanged.** Story 5.3 settled this file's rule: role-gate when the payload puts a named person's *performance* on the wire. `handler-benchmarks` ranks colleagues by speed; this table names the owner of a claim the caller can already read, attributes no metric to them, and — because `employer_scope` is the same predicate here as in the queue — shows a handler nothing her own queue does not already contain. So it follows `/summary` and `/charts`. The counter-argument is real and worth stating: this table exists to direct effort at named people, and a future column carrying a per-handler figure would move it across the line. That is a reason to keep the discriminator written down in the route docstring, not a reason to gate a claim list today.

**7. Two prototype defects, corrected deliberately.** `renderSV` cuts its top 30 with `.slice(0, 30)` over a `.filter(...)` in dataset order, so its "priority claims" table is priority-ordered in its heading only; and its action column reads `cpNextActions[0]`, a pre-authored copilot string, which is precisely what AD-2 forbids this column from being. Both are corrected here, and both are worth naming because the visual result differs from the prototype screenshot: the same thirty-ish claims in a different order, with different action text. The heading, the ten columns, the LITIG-instead-of-stage Status cell and the "top 30 of N" caption are ported exactly.

**8. Weighing in on the two deferrals parked for this story.** *The stage-group paging shape (from 2.1):* this endpoint answers the question that deferral was waiting on. A single-purpose list endpoint returning one `{items, nextCursor, total}` — rather than a groups map from which the client keeps one group and discards three — is what a paged list should look like, and it costs nothing extra to build. The recommendation for the queue is therefore the `groups` filter parameter (or a per-group endpoint) rather than a second response shape bolted onto the existing one; it is not in this story's scope, and the entry should be updated with that recommendation rather than closed. *Whether an action row may approve a payment (from 3.5):* this surface votes for "links, never approves". The worklist is read-only by role capability, its action column is a **label** and carries no command at all, and adding one would put the approvable-status rule in a third place. Nothing here wants an `approvePayment` member on `ActionCommand`; if that member is ever added, it should be for the checklist's own reasons and not because a supervisor's table asked for it.
