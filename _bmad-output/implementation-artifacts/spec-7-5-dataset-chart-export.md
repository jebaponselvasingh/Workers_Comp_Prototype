## Intent

**Problem:** The analyst workspace can now narrow a book nine ways, trend it, decompose its money and drill every figure to the claims behind it — and none of it can leave the screen. Offline analysis and audit requests are answered today by a person reading numbers off a chart, and the console has no record that they did. There is no export path anywhere in the build: no `csv` import, no `Content-Disposition`, no download route, and no audit action for PHI leaving the system.

**Approach:** One export capability across the four analyst sections. Six thin export routes, each mirroring the parameter surface of the aggregate route beside it, hand their filter spec to `services/worklist/export.py`, which re-runs **the same pure fold its sibling chart runs**, renders one rectangular table as CSV or XLSX, and streams it back as a browser download. Every successful export writes one content-free `audit_event` — actor, target, format, filter set, real row count — through a new `services/audit` entry point beside `record_copilot_approval`, which is already the shape for "a thing happened and its content is not the row's business". A rules-tier row cap bounds what one request may extract.

## Boundaries & Constraints

**Always:**
- **The export calls the function the chart calls.** Every target names one existing pure fold (`drill_through.select`, `fraud.panel_of`/`rates_of`, `trends.trends_of`, `decomposition.decomposition_of`/`adequacy_of`) and shapes its result into rows. No target re-derives a figure, re-counts a cohort, or re-sorts a ranking; an exported number that could differ from the displayed one is the failure this story exists to prevent.
- **The request carries a filter spec, never data.** No row, no claim id list, no client-held payload is ever sent up. Scope is the repository's (`employer_scope`), the caller's context is re-resolved server-side, and a tampered parameter can only narrow (AD-1/AD-7).
- **Nothing is persisted.** No `blobstore.put`, no new table, no `tempfile`, no path written under any volume. Bytes are produced in the request and handed to the response iterator; XLSX is built with `in_memory` so the writer does not spool to disk either (AD-11).
- **The audit event is content-free and precedes the bytes.** No claim value, no worker name, no cell content — the filter set, the format, the target and the row count, nothing else. It is emitted and committed *after* the table is materialised (so the count is real, never estimated) and *before* the first byte leaves, so an export that fails part-way is over-recorded rather than unrecorded.
- **The row cap is a rules-tier parameter**, versioned in a JDM document, and the refusal names its value (AD-8; `trend_periods.maxBuckets` and `TrendRangeTooWide` are the shape).
- Analyst-only, read-only, `no-store`, gate order `header → role → rules → service`, reusing `require_fraud_analytics_access` — the one analyst-workspace allowlist, never a second.
- The exported artifact is a **data product, not a screen**: DB snake_case column names, enum values as stored, dates ISO-8601, money as integer cents in a `*_cents` column. No preamble row, no formatted currency, no UI labels.
- Every export control is a per-surface control: it reports busy only on itself, never blocks the workspace, and never disables anything else.

**Block If:**
- Producing an exported figure requires a fold that does not already exist behind a rendered chart — that is a new analytics surface, not an export.
- Satisfying the "narrowed analyst at HTTP level" gap requires seeding a second analyst persona — that moves persona counts in Stories 1.3, 1.4 and 5.1 plus `e2e/fixtures/login.ts`, and this story's ACs never mention personas. Prove scope at service level as 7.1–7.4 did, and re-record the gap.
- Making the audit event answer "what was in the file" requires putting claim content in `before`/`after` — the AC forbids it and AD-11 forbids it.

**Never:** a client-side dump of the query cache or DOM; a saved-report library, export history UI, scheduled or emailed reports, PDF, or any delivery channel other than the caller's own browser download (BRD §7.4-8 real integrations stay deferred); an export of the AI red-flag narratives; an export affordance on any Epic 5 supervisor surface; a second money formatter; a new repository read.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|---|---|---|---|
| Dataset export | `GET /dashboard/claims/export?format=csv` as analyst, no filters | `200`, `text/csv`, `Content-Disposition: attachment`, one header row + 100 data rows, `Cache-Control: no-store`; one `audit_event` with `rows: 100` | No error expected |
| Filtered dataset | `…&filter[sector]=Aerospace&filter[surgery]=true` | Exactly the rows `GET /dashboard/claims` returns across all its pages for the same query, in the same rank order | No error expected |
| Chart aggregate | `GET /dashboard/financials/export?table=breakdown&groupBy=icd10` | The breakdown card's own groups, in its order, truncated exactly as the card truncates | No error expected |
| XLSX | `…?format=xlsx` | `200`, spreadsheet media type, a single worksheet whose cells equal the CSV's values | No error expected |
| Emptied segment | A filter set no claim satisfies | `200`, header row only, zero data rows; audit event with `rows: 0` | Never an error |
| Over the cap | A table longer than `export_limits.maxRows` | `422` problem+json `/problems/export-too-large`, naming the cap and the row count; **no audit event, no bytes** | `ExportTooLarge` → `_export_too_large` |
| Unknown target/format/table | `?format=pdf`, `?table=nonsense` | `422` before the service runs | FastAPI enum validation |
| Non-analyst | Supervisor or handler requests any export route | `403` problem+json `/problems/fraud-analytics-not-permitted`, before a claim row is read and before a rule document is loaded | `_fraud_forbidden` |
| Smuggled scope | `&employerId=…`, `&scopeAll=true`, `&userId=…` added by hand | Byte-identical file to the request without them | Ignored, not echoed |
| Export fails after the fold | Writer raises | Problem+json; **no audit event** (emission is after materialisation, so nothing is recorded for a table that was never rendered) | 500 handler |

**Acceptance Criteria:**
- Given an analyst session on any of the four workspace sections, when Export is clicked on a list or chart, then a file arrives whose rows are produced server-side under the caller's re-resolved scope from the same fold the surface rendered, and no byte of it was assembled in the browser.
- Given an active segmentation, when a surface is exported, then the file contains exactly the rows that surface is currently showing for that filter — and for a paged list, every page of them, not the pages that happen to be loaded.
- Given a successful export, when it completes, then exactly one `audit_event` exists naming the actor, the target, the format, the filter set and the real row count, containing no claim value or worker name, and it is durable before the first byte of the file leaves the server.
- Given an export that is refused — over the cap, or by role — then no audit event is written, no bytes are sent, and the caller receives problem+json that names the reason.
- Given a supervisor or handler session, when any export route is requested directly, then a 403 problem+json is returned before a claim row is read and before a rule document is loaded.
- Given an export in flight, when the analyst looks at the workspace, then only the clicked control reports busy, every other surface stays interactive, and completion is announced without blocking anything.
- Given the row cap is retuned in its rule document, when an export exceeding it is requested, then the refusal names the new value without a redeploy.

## Design Notes

**1. Streaming, honestly.** AC 3 says "streams or paginates without timing out". The build has one `StreamingResponse` (SSE) and no streaming *read*: every repository call materialises a list, and `select_drill_rows`' docstring refuses the `predicate` parameter that a paged export would need. The shape taken is therefore: one scoped read → the existing pure fold → the complete table, whose length is known **before the first byte** → the cap check → the audit row, committed → a `StreamingResponse` whose iterator encodes the already-materialised rows in chunks. That ordering is what makes the other two ACs possible at all: a chunked body cannot carry a problem+json after its headers have flushed, and a FastAPI request-scoped session is closed by the time a body iterator runs, so an audit row written *during* streaming would have no transaction to live in. The memory profile is the drill list's own, which is O(scope) and already recorded in `deferred-work.md`; what this story adds is a cap that bounds it explicitly rather than by luck.

**2. The cap is rules-tier, and the story file said Settings.** `7-5-dataset-chart-export.md`'s Dev Notes ask for `export_max_rows` in pydantic-settings. Two binding sources say otherwise: AD-8 gives JDM "weights, thresholds, bands, **caps**", and the Epic 7 context states outright that "export row caps are versioned rules-tier parameters". `trend_periods.maxBuckets` is the working precedent — a cap on how large an answer may be, owned by policy rather than arithmetic, with `TrendRangeTooWide` naming its value in the refusal. A number that decides how much PHI one request may extract is the same kind of number, and it belongs where a compliance owner can retune it with an effective date rather than a deploy.

**3. Content-free, and what that costs.** The audit row answers *who exported what slice, in what shape, how big* and nothing else. `entity_id` is a 16-hex digest of the canonical filter mapping so that "the same slice was exported three times last week" survives AD-11's redact-in-place, which erases `after` and keeps the skeleton. The format is written twice — into `action` (survives redaction) and into `after` (does not) — for exactly the reason `COPILOT_APPROVAL_PREFIX` gives for putting the outcome in `action`. The filter *values* are query terms: an employer id, an ICD-10 code, a severity band. They are not claim values, and the test that proves it scans the serialised payload for a seeded worker's name rather than checking key names.

**4. Why `record_export` lives in `services/audit` and commits.** `test_exactly_one_module_constructs_each_append_only_row` pins `AuditEvent(` to that module; `test_no_router_writes_through_a_session` forbids the router committing. An export has no mutating command to ride along with, which is precisely `record_copilot_approval`'s situation and precisely why that function is the one exception to `record`'s no-commit rule. A second such entry point beside it is the smallest correct shape.

**5. A data product, not a screenshot.** Money leaves as integer cents in a `*_cents` column, enums as their stored snake_case values, dates as ISO-8601, booleans as `true`/`false`, and there is no preamble row — a comment line above the header breaks every CSV parser that would consume this. That reading is the story's own: it puts money in the same sentence as "enum values as DB snake_case" and "dates ISO-8601", all three under "export is a data product, not a UI". It also keeps `web/src/lib/money.ts:33` the only division by 100 in the build. XLSX writes integers as numbers and dates as ISO strings rather than Excel serial dates, so the two formats hold the same values and a test can compare them cell for cell.

**6. Columns are the drill projection; rows are the screen's rows.** The claim export publishes every field `select_drill_rows` already loaded under the caller's scope — 28 columns plus the six derived flags and the priority score — not the fourteen the list card renders. Nothing new leaves the database: the read is the one the list already takes, and an analyst entitled to the list is entitled to the columns behind it. What "exactly what is on screen" governs is the **row** set, which is where a scope or filter error would live.

**7. Eight targets, and the two that are missing.** The red-flag frequency card is not exportable: it is the one analyst surface whose content is model output, held by AD-10 to be labelled, timestamped and never authoritative, and a CSV strips exactly the labelling that makes that true. The financial Totals tiles are not exportable either — `KpiCard` wraps its body in a `<Link>`, so a button inside it would be invalid markup, and all three figures already travel on the breakdown export. Both omissions are decisions, so both are stated on the surfaces that lack the control.

**8. Two buttons, not a menu.** `SegmentationBar.tsx` already ruled that the vendored `select`/popover primitives are for a control that needs a custom option row and that "a list of plain strings is not that". Two formats are not that either. And failures stay inline at the control while successes toast, because `toast.tsx` says so in as many words — which is also the honest split: a completion notification is something you may miss, a refusal is something you must not.
