# Adversarial Review — Agent Harness v1.3 (create_agent + HumanInTheLoopMiddleware swap)

- **Target:** ARCHITECTURE-SPINE.md, agent harness as amended v1.3 — AD-6, AD-13, AD-14, and their touchpoints (AD-4 Write-concurrency convention, AD-7 caller scope, AD-11 PHI, the Copilot stream convention, the Testing & CI convention).
- **Under attack:** the v1.3 amendment that (a) makes the free-chat / tool-calling core a `langchain.agents.create_agent` harness embedded as a node in a deterministic supervisor-router StateGraph, and (b) replaces the old "write tools never LLM-selectable + approval-token" gate with `HumanInTheLoopMiddleware` (`interrupt_on` the write tools; `allowed_decisions: approve | edit | reject`), write tools now **registered on the agent** (model may select) with the registry-raise kept only as defence-in-depth.
- **Method:** Two-unit divergence attack. Each finding constructs two builds one level down that obey every AD **to the letter** yet integrate incompatibly (clashing shared-data shape, two owners of one entity, conflicting control/state paths, or wire-protocol mismatch). Judged against what the spine *says*, not what a sensible engineer would infer. The prior review's F1–F13 fixes are now in the spine text; this review attacks only what the `create_agent`/HITL swap newly opened.
- **Date:** 2026-08-10
- **Verdict:** **FAIL for parallel build.** The swap correctly closes the old node-vs-tool gate, but the new `edit` decision, the middleware-vs-registry double gate, the router-node RTW write path, and the interrupt/resume wire shape are each underspecified or self-contradictory. Five findings are HIGH and integration-fatal on first contact; two are MEDIUM. The middleware↔registry approval-signal contract (F4-v13) and the RTW-on-a-router-node gate (F6-v13) are each independently sufficient to deadlock or silently un-gate the core write-approval feature.

## The two units

- **Unit A — Copilot backend team.** Owns `server/agents/` (StateGraph supervisor router, the `create_agent` core, `agents/state.py`, `agents/tools/` registry, `HumanInTheLoopMiddleware` wiring, prompts, AsyncPostgresSaver), the AD-4 approve-execution path it triggers, and the copilot SSE endpoint in `server/api/`.
- **Unit B — Copilot frontend team.** Owns `web/features/copilot` on the assistant-ui LangGraph runtime (`@assistant-ui/react-langgraph` 0.14.x, per AD-9), consuming the SSE stream and driving the resume path.
- Where a finding is intra-backend, the parties are **Engineer A1** (write tools + the middleware gate + approve-execution) and **Engineer A2** (registry defence-in-depth + RAG/insight nodes), both inside Unit A.

## Findings

### F1-v13 — HIGH — The `edit` decision can retarget the entity or defeat the drafted-version CAS

AD-6: "The gated tool call records the `version` of every entity it was drafted against; on `approve`, the write goes through AD-4 commands compare-and-swapped on those versions … on `edit`, the human-revised arguments replace the model's before execution." The Write-concurrency convention: "Copilot approval writes CAS on the versions recorded in `pending_approval`." **Nothing in the spine says an `edit` may not change the target entity, and nothing says whether the recorded version set is re-resolved, frozen, or re-validated when the human rewrites the arguments.** The recorded versions were captured against the entity the *model* selected; `edit` mutates the arguments after that capture.

- **Engineer A1** (draft-time-versions reading): captures `{entity_id → version}` at interrupt time from the model's proposed args, then on `approve`/`edit` CASes on that frozen map. A human `edit` that changes the target claim (WC-1001 → WC-1002) leaves the map keyed to WC-1001. A1 either (a) CASes WC-1002 against WC-1001's recorded version number — which *succeeds* whenever the two versions coincide (both at v3), writing the edited payload to the **wrong entity** past a version guard that was never checked against it, or (b) finds no map entry for WC-1002 and treats "no recorded version" as "unguarded write" — an unguarded read-modify-write, which AD-4 flatly forbids ("no command performs an unguarded read-modify-write").
- **Engineer A2** (re-resolve-on-approval reading): treats `edit` as "the human may revise anything including the target," and therefore re-resolves the version from fresh state at approval time for whatever entity the final args name. This is safe against cross-entity edits — but it **defeats the AD-6 stale-safe invariant**: "a stale approval fails safe (the command 409s …)." Resolving the version at approve time instead of draft time means there is no draft-vs-now comparison; a claim that changed between draft and approval is silently written over. A2 obeys "CAS on the versions recorded in `pending_approval`" only in name — it re-derives them.

Both readings satisfy every written word. A1 can cross entities or drop the guard; A2 nullifies stale-safety. They also disagree on what AD-4 records in `after` (model args vs human-edited args) and who the `actor_id` is on an edited write. First integration: an edited RTW-letter save and an edited reserve change land on different entities/versions depending on which engineer wrote which half.

**Fix (tighten AD-6 + Write-concurrency convention):** "An `edit` decision may revise only the *arguments* of the already-selected write tool; `entity`, `entity_id`, and the recorded version set are **frozen at interrupt time** and immutable across `edit`. An edit whose revised arguments would target a different entity_id is a protocol error, rejected without execution (the model must re-propose a fresh write). On `approve` **and** `edit`, the AD-4 command CASes on the draft-time recorded versions — never re-resolved — so both decisions inherit the stale-safe 409 path. The AD-4 audit `before/after` records the post-edit arguments; `actor_id` is the approving user; an `edit` additionally records that the arguments were human-revised."

### F2-v13 — HIGH — Two write tools in one AI message: the F5 "one `pending_approval`" invariant vs HITL's native multi-request interrupt

AD-6 (the folded-in F5 fix): "at most one `pending_approval` … exists per thread — a second claim-write in one run sequences as a second interrupt after the first resolves." **The spine asserts sequential single-interrupt behavior but never specifies the mechanism that produces it** given that the core is now `create_agent` with `HumanInTheLoopMiddleware`, whose documented behavior is to batch every `interrupt_on` tool call in one AI message into a **single interrupt carrying an array of action requests**, resolved by an array of decisions.

- **Engineer A1** (letter of AD-6): enforces at-most-one by construction — configures the core so the model can never surface two write tool calls at once (parallel tool calls disabled for write tools, or a custom pre-model/post-model middleware that defers all but the first write tool call to a later turn). One interrupt = one request; resume = one decision. Matches AD-6's "second interrupt after the first resolves."
- **Engineer A2** (letter of "middleware-gated write tools"): takes `HumanInTheLoopMiddleware`'s native behavior. When the model emits `update_reserve(WC-1001)` and `save_rtw_letter(WC-1001)` in one turn, the middleware raises one interrupt with two requests. A2 renders both, resumes with `[approve, approve]`. A2 violated no written rule — AD-13 says "every `kind: write` tool is … gated by `HumanInTheLoopMiddleware`," and A2 used exactly that. But now **two `pending_approval`s exist at once**, breaking the F5 invariant, and the interrupt/resume payloads are arrays, not scalars.

The two build incompatibly at the wire *and* the invariant: A1's `interrupt` event carries one request and its resume carries one decision; A2's carries N of each. Unit B (frontend), reading the same spec, will render either a single approval card or a multi-action card — the resume shape it POSTs won't match whichever backend engineer shipped. The single-flight guarantee the F5 fix exists to provide is silently absent in the A2 build.

**Fix (tighten AD-6):** "The `create_agent` core is configured so at most one `kind: write` tool call may be pending per model turn (parallel write-tool selection disabled; additional write tool calls in one AI message are deferred, not co-interrupted). The `interrupt` payload therefore always carries **exactly one** action request and resume carries exactly one decision. This reconciles `HumanInTheLoopMiddleware`'s array-interrupt default with the at-most-one-`pending_approval` invariant; the graph/routing unit test (Testing & CI convention) asserts a two-write turn produces two sequential single-request interrupts, not one two-request interrupt."

### F3-v13 — HIGH — Agent-initiated AI-insight refresh is a write, is interrupt-exempt, and the registry defence-in-depth forbids exactly that

AD-6: "Agent-initiated AI-insight refresh goes through the owning `services/rag` command (AD-12) and is **exempt from the interrupt gate** but not from audit." AD-13: "Every `kind: write` tool is registered on the `create_agent` core but **gated by `HumanInTheLoopMiddleware`**" and, defence-in-depth, "the registry still **refuses a write tool executed outside an approved interrupt** (raises without the middleware's approval in graph state)." AD-12/AD-10: `ai_insight` is an owned entity refreshed via a `services/rag` command; a refresh **mutates** it. AD-4 binds "agent-initiated writes." So the refresh is unambiguously a write — yet it must run with no interrupt and no approval-in-state. **The three rules cannot all hold for one tool.**

- **Engineer A2** (honest-kind reading, AD-13 + AD-4): the refresh tool mutates `ai_insight`, so it is `kind: write`. Per AD-13 that lands it in `interrupt_on` and the registry guard. Result: a background insight refresh pauses the run for a human approval card (contradicts AD-6's exemption), and if forced through, the registry guard raises because there is no approval in graph state — **the exempt refresh is impossible to execute as written.**
- **Engineer A1** (honor-the-exemption reading, AD-6): to keep the refresh interrupt-exempt, A1 either relabels it `kind: read` (violating AD-13's honest `read | write` contract and AD-4's write-command routing — and AD-13 even calls a `services/rag` retrieval "a registered read tool," conflating retrieval-read with refresh-write) or leaves it `kind: write` but excludes it from `interrupt_on` and carves it out of the registry guard's raise. That carve-out **punches exactly the hole the defence-in-depth exists to seal**: once the guard admits one unapproved write "because it's the exempt refresh," a hand-added node can claim the same exemption and the "no write without approval" universal is gone.

Both engineers are defensible; they build opposite mechanisms (gate-it vs carve-it-out), and the registry guard is either a refresh-blocker or a sieve depending on who wins.

**Fix (introduce a third tool kind + tighten AD-6/AD-13):** "Tool `kind` is `read | write:gated | write:autonomous`. `write:gated` (claim/document/diary/meeting/email writes) is registered on the core, in `interrupt_on`, and blocked by the registry guard absent an approved interrupt. `write:autonomous` is the single owner-initiated exception — today only `services/rag`'s AI-insight refresh: it is **not** in `interrupt_on`, is audited per AD-4, and the registry guard admits it via an explicit allowlist keyed to the owning service, never a per-tool opt-out. AD-6's interrupt-exemption is stated in terms of `write:autonomous`. No `write:gated` tool may be relabelled to obtain the exemption; adding a `write:autonomous` tool is an AD-level change, reviewed."

### F4-v13 — HIGH — The middleware↔registry approval signal is unnamed: the double gate deadlocks or the defence-in-depth is vacuous

AD-6: "the model may *select* a write tool but can never execute one unapproved (the F1 gate is the per-tool middleware, not tool-hiding)." AD-13: the registry "refuses a write tool executed outside an approved interrupt (**raises without the middleware's approval in graph state**)." This posits two gates and an interface between them — the registry reads "the middleware's approval in graph state" to decide whether to raise. **The spine never names that state artifact, and `HumanInTheLoopMiddleware` does not natively write an approval token into a user-declared state channel** — on resume it lets the gated tool call proceed through its own execution path; it does not stamp `agents/state.py`'s `pending_approval` (or any channel) with "approved" for a downstream guard to read.

- **Engineer A1** (middleware-is-the-gate reading): builds the flow so resume → the middleware's own execution proceeds; there is no separate approval marker because the middleware *is* the enforcement. A1 populates no channel the registry reads. Consequence: A2's registry guard, looking for "the middleware's approval in graph state," finds nothing and **raises on every write — including approved ones. No copilot write ever succeeds. Deadlock.**
- **Engineer A2** (registry-is-the-gate reading): implements the guard against a concrete channel it invents — e.g. an `approved_tool_call_id` it expects the approve path to set. But that channel is not in AD-6's closed schema (`messages, caller, claim_id, pending_approval, …`), and AD-6 forbids adding channels node-locally ("new channels are added [to `agents/state.py`] via review, never node-locally"). If A2 instead keys on `pending_approval.decision == approve`, but A1's approve path clears `pending_approval` on resolution (AD-6 only spells out clearing on reject), the guard again finds nothing and raises. If A2 makes the guard lenient to avoid the deadlock, the guard never actually blocks anything — the defence-in-depth is **vacuous**, and AD-13's promise that "a hand-added node cannot bypass the gate" is false.

Every combination is broken: deadlock, or a silently disabled second gate. The two units cannot agree because the spine never defines the approval signal's name, writer, reader, or lifecycle.

**Fix (tighten AD-6 + AD-13 with a named contract):** "The approval signal is explicit and single-sourced. On an `approve`/`edit` resume, `HumanInTheLoopMiddleware` records the approved tool call id into a declared `pending_approval.approved_call_id` field in `agents/state.py`; the registry guard raises unless the executing write tool call's id equals `pending_approval.approved_call_id` for the current run. `pending_approval` (including `approved_call_id` and the recorded versions) is written **only** by the middleware/approve path and cleared on terminal resolution of that call — it is one owned channel, not two writers. The graph unit test asserts: (a) an approved write executes exactly once; (b) a tool call whose id is absent from `approved_call_id` raises; (c) clearing timing does not strand a second sequential interrupt (F2-v13)."

### F5-v13 — HIGH — The `approve/edit/reject` interrupt+resume shape has no wire mapping to the assistant-ui stream contract

Copilot stream convention: event set `messages | updates | interrupt | error | done`; "Resume is a POST to the same runs endpoint with the runtime's `command: {resume: …}` payload." AD-6 fixes `allowed_decisions: approve | edit | reject`. **What the `interrupt` event's payload contains and what the inner shape of `command: {resume: …}` must be — list vs object, field names, how `edit` carries revised args, how `reject` is spelled — is entirely unspecified**, and it straddles the Unit A / Unit B boundary. It is also a vocabulary mismatch: the LangGraph/assistant-ui HITL convention commonly speaks `accept | edit | response | ignore`, while the spine says `approve | edit | reject`.

- **Unit A** (backend) emits the interrupt as `HumanInTheLoopMiddleware`'s native `HumanInterrupt`/action-request structure and expects `command: {resume: [{type: "approve", args?}]}` (a list of `HumanResponse`), using the spine's `approve/edit/reject` literals.
- **Unit B** (frontend, `@assistant-ui/react-langgraph` 0.14.x) constructs the resume per the runtime's own convention. If it emits `command: {resume: {decision: "approve", editedArgs: {...}}}` (a scalar with `decision`/`editedArgs`), or uses the runtime's `accept/edit/respond` vocabulary, the round-trip fails: the backend can't parse the decision, the `edit` args arrive under the wrong key, or `reject` is sent as `ignore`. Both units satisfied "speaks the stream protocol the assistant-ui LangGraph runtime consumes" and "the runtime's `command: {resume: …}` payload" — because the spine names the envelope but not the contents.

The AD-15 gate does not catch this: it tests "the `HumanInTheLoopMiddleware` approve/edit/reject round-trip against the **stub's scripted write-proposal**" — the stub is a *model* stub (chat/embeddings), not a frontend-wire stub, so the E2E can pass against Unit A's internal shape while Unit B's real resume payload still mismatches. First HITL approval in the browser hangs.

**Fix (new Copilot-stream convention sub-row + AD-6):** "The `interrupt` event payload is pinned: `{tool, entity, entity_id, args, recorded_versions, allowed_decisions}`. The resume payload is pinned to the exact `@assistant-ui/react-langgraph` 0.14.x / `@langchain/langgraph-sdk` shape: `command: {resume: [{type: 'approve' | 'edit' | 'reject', args?}]}` (a list; `edit` carries the full revised `args`; `reject` carries none). The `approve/edit/reject` ↔ runtime-vocabulary mapping lives in one canonical adapter module owned by Unit A and imported by the generated client, so both sides derive it from one source. The AD-15 integration test asserts this exact wire shape end to end (not merely the backend round-trip)."

### F6-v13 — HIGH — RTW letter is a router-node QAS write, but the HITL gate lives on the `create_agent` core — the gating mechanism for router-node writes is undefined

AD-14: "the RTW letter **is** a QAS key whose node runs tool-merge → LLM prose → the `HumanInTheLoopMiddleware` write-tool gate (AD-6)." AD-6/AD-13: `HumanInTheLoopMiddleware` is a middleware **on the `create_agent` core**, and QAS keys "route through a static key→node map in the supervisor router **before any LLM call**; only free-text messages go to the `create_agent` core." So the RTW node is a *router* node, outside the core — yet AD-14 requires its write to be gated by a middleware bound to a *different* subgraph (the core). **The spine never says how a deterministic router-node write is subjected to a middleware that only wraps the core's model/tool loop.**

- **Engineer A1** (router-node reading, AD-14 topology): builds the RTW node as a plain router node that, after LLM prose, calls the registry's `save_rtw_letter` write tool directly. The core's `HumanInTheLoopMiddleware` never sees this invocation (the node isn't inside the core's loop), so **no interrupt fires**. Then A2's registry defence-in-depth (F3-v13/F4-v13) raises — no approval in state — and the RTW letter can never be saved; or, if the guard is lenient, the write executes with **no approval gate at all**, exactly what AD-6 forbids.
- **Engineer A2** (gate-must-fire reading, AD-6): to make the middleware fire, A2 routes the RTW write back **through the `create_agent` core** (re-enter the core with the write tool "selected") so the core's middleware interrupts. But AD-14 says QAS routing happens "before any LLM call" and only free-text goes to the core; a deterministic node "invoking" the core's middleware for one pre-chosen tool is not a described capability, and it contradicts the router topology. A2's mechanism is unspecified and diverges from A1's.

Both cite AD-14 and AD-6 verbatim and build opposite things: a direct router-node write (ungated or dead) vs a re-entry into the core (topology-violating and undefined). The single most visible write feature — the RTW letter — has no agreed gate path.

**Fix (tighten AD-6 + AD-14):** "`HumanInTheLoopMiddleware` gates every `kind: write:gated` tool **wherever invoked** — the gate is a property of the tool invocation through the registry, not of the core subgraph alone. Concretely: write-tool interrupts are raised by a shared gate wrapper applied at the registry boundary (the same wrapper the core's middleware uses), so a QAS/router node that calls a write tool raises the identical `interrupt()` with the identical payload and resume contract as the core. The RTW QAS node therefore runs tool-merge → LLM prose → registry write-tool call → shared gate interrupt, streamed and resumed identically to a free-chat write. No write path exists that reaches an AD-4 command without traversing the shared gate."

### F7-v13 — MEDIUM — AD-7 re-resolution on resume vs AD-6 approve path: scope revoked mid-approval yields an undefined 403-on-approve

AD-7: "on every run start **and every resume**, the API dependency re-resolves the context from `app_user` + `user_employer_assignment` and overwrites the [`caller`] channel, so a resumed thread never replays yesterday's book of business." AD-6's approve path specifies only the **version** outcome: "on `approve`, the write goes through AD-4 commands compare-and-swapped on those versions — a stale approval fails safe (the command 409s …)." **It says nothing about a scope change between draft and approval.** A write is drafted for a claim under employer X; before the user approves, their `user_employer_assignment` to X is revoked. On resume, AD-7 mandates re-resolving `caller` — the user is now out of scope for that claim.

- **Engineer A1** (AD-7 literal): passes the re-resolved (post-resume) caller to the AD-4 command; the repository's unconditional employer filter (AD-7) now excludes the claim, so the approved write fails with a **not-found / 403**, not a 409. AD-6's stale-safe machinery handles only the 409 (version) path — there is no defined behavior for "approved write blocked by scope revoked mid-approval." A1 must invent one (silent drop? error toast? discard proposal?).
- **Engineer A2** (approve-path literal): reads AD-6's approve path as "CAS on recorded versions and write," and reuses the caller captured at draft time (the context the proposal "was drafted against"), so the write succeeds — **violating AD-7's mandate that a resumed thread never replays yesterday's book of business.**

A1 obeys AD-7 and hits an unspecified 403 path; A2 obeys AD-6's terse approve wording and breaks AD-7. Different failure/success semantics for the same revoked-mid-approval case.

**Fix (tighten AD-6 approve path):** "On `approve`/`edit`, the AD-4 command runs under the **resume-time re-resolved** caller context (AD-7). A scope loss between draft and approval fails safe exactly as a version conflict does: the command is blocked, the graph discards the proposal, and streams an assistant message that the user no longer has access to draft this write — it never executes against a stale scope. AD-6 enumerates both fail-safe causes: stale version (409) and revoked scope (403)."

### F8-v13 — MEDIUM — `record_copilot_approval` has no defined shape: a second audit record shape drifts from AD-4

AD-6: both approve and reject branches "record the outcome (action kind, claim, actor, timestamp — **no content**) via a `services/audit` `record_copilot_approval` command; that is the only persistence permitted on the reject branch." AD-4 fixes one audit shape: `(id, at, actor_id, actor_role, action, entity, entity_id, before, after)` with `before/after` as JSONB diffs, and exists precisely to prevent "per-team audit-record shapes drifting." **A "no content" record has no `before/after` — so is `record_copilot_approval` an `audit_event` row with null diffs, or a separate table?** The spine doesn't say.

- **Engineer A1** writes it as an `audit_event` row with `action: copilot_approval` and `before/after = null`. But AD-4 declares `before/after` the JSONB diff of a mutation; a null-diff audit row for a *non-mutation* (reject) stretches the fixed schema, and the append-only `audit_event` now carries rows that aren't mutations — consumers filtering audit history by entity diffs get empty/None rows they must special-case.
- **Engineer A2** writes it to a dedicated `copilot_approval_log` table with its own columns — a **second audit-record shape**, the exact drift AD-4 forbids, and a store AD-11's purge cascade must now separately know about (it enumerates PHI-class stores; a new table added under the radar risks being missed by purge).

Both cite AD-6's `record_copilot_approval` and build divergent persistence; audit consumers and the purge cascade see two different worlds.

**Fix (tighten AD-6 + AD-4):** "`record_copilot_approval` writes an `audit_event` row using the fixed AD-4 schema, with `action: copilot_approval_{approved|rejected}`, `entity/entity_id` = the proposed target, and `before/after` = the redaction marker (never proposal content — consistent with the AD-11 'no content' rule). No separate approval table is created; the append-only `audit_event` store and its purge disposition remain the single audit shape."

## Note on what the swap fixed vs opened

The v1.3 amendment cleanly closes the prior review's F1 (write tools are now middleware-gated, not node-gated) and hardens F5/F7/F11 in text. But moving the gate from a bespoke approval-token mechanism onto `HumanInTheLoopMiddleware` + `create_agent` imports the framework's *own* contracts (array interrupts, native resume vocabulary, middleware-scoped-to-core execution, no user-visible approval channel) that the spine's prose does not yet reconcile with its invariants. The six HIGH/MEDIUM seams above are all at that spine-text-vs-framework-behavior boundary; each is closable with the tightening shown without changing the chosen stack.
