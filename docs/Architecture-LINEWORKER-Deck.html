Starting point

The prototype is a spec, not a seed

What it is

One 560 KB HTML file: ~100 claims hardcoded in JS, all logic in the browser, role scoping client-side, zero persistence, copilot always falling back to canned cp* answers.

Why it's valuable

The Excel maps all 93 UI elements to calculation logic and target Table.Column. The BRD enumerates every FR. Together they are a near-complete requirements + data-model spec.

The clean split it reveals

Deterministic rules (benefit, priority, reserve) · AI narration (7 quick-action prompts) · rendering. The architecture preserves exactly this split.

Must not survive

Client-side HANDLER_MAP scoping · derived flags stored beside inputs · credential-less cloud fetch · canned offlineAnswer text presented as AI · alert() dialogs · logic in innerHTML templates.

Ports almost verbatim

SVG body map · the 7 QAS prompt templates · benefit/priority/reserve formulas · the 100-claim dataset as seed data.

Hard constraints

AI inference fully local via Ollama — no cloud APIs. Agent layer on LangChain + LangGraph. HIPAA-adjacent PHI stays on-prem.

System shape · AD-1

Layered & API-first — agents behind the same boundary

Dependencies point one way. If a number appears on screen, a service computed it. Agents consume services as LangGraph tools — never SQLAlchemy, never the API, never unscoped data.

The contract

Fourteen invariants keep independent builders aligned

AD-1

SPA renders only; every computation & mutation behind FastAPI

AD-2

Financial logic exists once in Python; LLM narrates tool output, never originates figures

AD-3

One PostgreSQL owns rows + vectors + checkpoints + cache + audit

AD-4

Writes are version-guarded (CAS) service commands with same-transaction, append-only audit events

AD-5

Local-only Ollama; model names are config; no cloud path exists

AD-6

One copilot StateGraph; single-flight (scope, user, seq) threads; AI writes require interrupt() and fail safe when stale

AD-7

One app_user + assignment model scopes every role, enforced in repositories — scope gates visibility, role gates capability

AD-8

JDM owns parameters & decision tables; Python owns formulas; never both

AD-9

TanStack Query + shared queryKeys; optimistic updates for user-entered scalars only; 409 renders the conflict inline

AD-10

One registered computer per derived field (embeddings included); AI narratives live in the ai_insight cache

AD-11

Everything claim-derived is PHI-class — audit diffs included: encrypted, log-banned, one purge cascade with redact-in-place audit

AD-12

Exactly one write-owning service per entity (capability map = registry)

AD-13

Agent tools are thin registry entries wrapping one service call; write tools never LLM-selectable — execute only after approval

AD-14

Quick actions route deterministically before any LLM call; outages degrade honestly — no canned answers, claim ops unaffected

Data · AD-3 / 10 / 12

One database, one owner per table, one computer per derived value

Derived, never stored editable

days_open, risk, payment_due, rtw_blocked, totals — one registered function each in services/derivations; queue chip and detail badge can't disagree.

Canonical payment transition

Approve ⇒ payment_scheduled; only the payment batch marks paid. Money is integer cents in DB, API, and across the ZEN boundary.

Write-back = audited, version-guarded commands

The Excel's Review / Confirm / Approve-Payment semantics become service commands that CAS on version — concurrent edits get a 409 with fresh state, never a silent clobber; worklist and ledgers stay in sync by reading the same row.

Rules · AD-2 / AD-8

Two tiers: business-tunable parameters vs statutory formulas

ZEN JDM documents (config)

  • Priority-score weights (+40 litigation, +35 SIU, …)
  • Reserve adequacy bands (115% / 60%)
  • SLA targets (pick <1d · approve <5d · settle <30d · RTW >80%)
  • Worklist 7-item cap · handler-benchmark thresholds

Versioned in the DB with effective dates · visual graph editor · hot reload · git-diffable JSON.

Typed Python (code)

  • Benefit calc: comp-rate % of AWW, clamped to state statutory min/max, 7-day wait
  • Score arithmetic & schedule construction
  • Reserve-check computation
  • SLA aggregation

Property-tested (Hypothesis) against statutory ranges · reads its tunables from ZEN.

A rule element exists in exactly one tier — never both. That single sentence closes the fork the prototype invites, where the same weight could live in a config table and a formula.

Structured output

with_structured_output(method="json_schema") — Ollama's native constrained generation; fraud lists & action rankings validate against Pydantic before the UI sees them.

No cloud path

The prototype's credential-less fetch to api.anthropic.com has no successor — not even as fallback. Ollama's port is never published.

Re-benchmark before pinning

Model rankings are practitioner-blog grade and move quarterly; qwen3 is directional until tested on project prompts (Deferred).

AI · AD-2 / 6 / 7 / 13 / 14

One copilot graph · figures from tools · writes human-gated

Figures from tools — the reserve node calls reserveCheck and narrates; it cannot invent an adequacy verdict. Tools are thin registry entries wrapping exactly one service call (AD-13).

Scope in graph state, re-resolved — the registry injects the caller's book-of-business into every tool call; scope is re-resolved on every run start and resume, so a resumed thread never replays yesterday's assignments.

Writes gated & stale-safe — write tools are never LLM-selectable; the model only proposes. Approval executes a version-guarded AD-4 command — stale approvals fail safe. Ollama down? Deterministic actions keep working; LLM routes return ai_unavailable, never canned text (AD-14).

Compliance · AD-4 / 7 / 11

PHI posture — WC data is HIPAA-adjacent

ControlMechanism
AuthorizationRepository-layer RBAC from app_user + user_employer_assignment (one model for all roles; scope gates visibility, role gates capability) — REST, aggregates, agent tools, and vector search all scoped; no caller-supplied scope, no role bypass, ever
AuditFixed-schema event per mutation, same transaction; audit_event INSERT-only for the app role (sole exception: the audit_redactor role used by purge/retention jobs); 7-year default retention; pgaudit beneath, DML value-logging disabled
EncryptionTLS at ingress & to Postgres; encrypted volumes (DB logs included); backups encrypted before leaving the host
AI containmentLocal inference only; chat checkpoints classified PHI; prompts & outputs never in operational logs; write tools never LLM-selectable; outages degrade honestly
LifecycleOne purge cascade (owner: services/audit) covers rows, embeddings, checkpoints, cache, binaries — and redacts audit diffs in place, so purged claims aren't resurrectable from audit

The one-database decision is load-bearing: exactly one place PHI lives, one backup stream to encrypt, one purge implementation to audit. Local-only AI removes the model-vendor BAA problem entirely.

Operations

On-prem Docker Compose, single site

Hardware

24 GB GPU (4090-class) runs qwen3:14b + bge-m3; 48 GB unlocks 32B. VRAM floor = Q4 download size + 2–6 GB KV cache.

Environments

dev: Compose, CPU models OK. prod: GPU, TLS, encrypted volumes, off-host backups. No K8s until scale demands.

CI gate

Lint + typecheck + tests each merge; migrations apply clean to a fresh DB; financials carry property-based tests.
